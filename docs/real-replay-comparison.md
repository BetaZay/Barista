# Compare real Wii U video through the Barista connection

**Archived experiment:** physical replay did not work in the attempted trial,
and the user requested abandoning this route. These scripts and preparation
notes are retained for reference. They are not the normal test workflow and
must not be resumed without a new user request. Use the Release-based live
workflow in [capture-workflow.md](capture-workflow.md) for ongoing trials.

The controlled comparison uses the same captured scene three ways. Each trial
needs its own GamePad connection and radio/host capture. Cemu is not involved.

| Trial | Video source | What it exercises |
| --- | --- | --- |
| A: original packet replay | Real console compressed bytes and packet boundaries | Barista connection, clock translation, UDP sending and radio |
| B: re-encoded packet replay | A decoded, then encoded by Barista's native encoder | Same replay sender, with Barista compressed video |
| C: normal engine playback | A decoded into a lossless video file | Normal live encoder, frame/chunk scheduling and recovery |

A retains captured options, formats, PCM and relative send offsets. Timestamps
are translated to the current connection's hardware clock; video and PCM
sequence numbers are regenerated. Encrypted Wi-Fi frames cannot simply be
resent: the new association has fresh keys and replay counters.

B retains A's format and PCM records exactly, along with frame types and chunk
send windows. Compressed size changes can require different packet counts or
lengths; the preparation report counts affected chunks. It uses the production
native encoder, but bypasses live frame scheduling and recovery decisions.

C tests those live decisions too, so a B/C difference does not isolate the
encoder alone. Its audio and format messages are generated by the normal file
pipeline, rather than taken from A. The source retains the full decoded
864-by-480 image, including normally cropped columns, without stretching.

## Prepare the comparison

Build first, then use an authenticated decrypted IP capture:

```sh
cmake --build build --parallel 4
python3 scripts/prepare-replay-comparison.py \
  /tmp/wiiu-reference-review-ip.pcap /tmp/wiiu-fresh-replay-comparison
```

The output directory must be new. It contains `original.drcrep`,
`reencoded.drcrep`, restored Annex B `original.h264` and `reencoded.h264`, and
lossless `source.mkv` for normal engine playback. `comparison.json` records
source/encoder hashes, frame counts, packet differences and validation.
Both H.264 variants must strictly decode all selected frames. The lossless
file's decoded pixel hashes must match the original H.264 exactly.

The extractor requires a complete IDR-led chain with matching preceding
format messages. A missing video or format observation ends that chain; it
resumes only at another complete IDR. Format-only slots inside the selected
window are retained. It never fills capture gaps with invented packets.

## Physical trials

Stop an existing Barista session first, and keep the GamePad off until capture
is ready. The service normally supplies an AppHook input; it does not expose
the replay environment variable. These diagnostic trials therefore use the
installed root-owned engine directly, with one-time Polkit elevation.
The existing passwordless capture action still handles capture and analysis.

Run A with:

```sh
python3 scripts/run-replay-experiment.py \
  /tmp/wiiu-fresh-replay-comparison --trial original --seconds 60
```

The runner starts the installed engine and capture helper, rings the terminal
bell at `READY`, records input/engine hashes and saves separate engine/capture
logs. Turn on the GamePad after the bell. Playback starts automatically; there
is no need to launch Cemu. The engine's one-time Polkit elevation may prompt;
the existing passwordless capture action is unchanged. Capture restores wlan1
and analyzes the result; the runner then shuts down its own engine through a
user-owned control socket. A privileged timeout also bounds engine lifetime
if the runner dies.

Repeat B and C:

```sh
python3 scripts/run-replay-experiment.py \
  /tmp/wiiu-fresh-replay-comparison --trial reencoded --seconds 60
python3 scripts/run-replay-experiment.py \
  /tmp/wiiu-fresh-replay-comparison --trial live --seconds 60
```

Keep the GamePad off between trials until the next bell. Save each `RESULT`
directory and note whether corruption appears within the clip, at its loop
boundary, or both. Ctrl-C closes the capture's lifetime pipe and requests
engine shutdown.

Use the same capture duration and preferably repeat A after B/C to check
whether radio conditions changed. Analyze each capture's timing, delivery and
recovery requests alongside visual observations. Requests can repeat while
waiting for an IDR; their count is not a count of visibly corrupt frames.

If A looks clean and B fails, the encoder or changed compressed sizes/packet
counts become stronger suspects. If A and B look clean while C fails, focus
on the normal media pipeline's scheduling, packet options and recovery.
If A also fails, encoder changes alone cannot explain the failure: investigate
the connection, replay timing, bootstrap and radio delivery. These are leads,
not proofs. Replay loops deliberately restart at an IDR, and this short clip
may conceal faults which require a longer reference chain.
